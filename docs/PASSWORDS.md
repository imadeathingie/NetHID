# Changing the login password

The web UI's password lives in `env.h` and is compiled into the firmware. It can
also be changed from the device itself — header cog → **Password** — without a
rebuild.

```
Password        changed on this device
[ current password        ]
[ new password            ]
[ repeat new password     ]
[ Change password ] [ Revert to firmware password ]
```

The panel is in the page shell, not in a tab, so every user sees it on every
build regardless of which tabs they were granted.

## Forgetting it does not brick anything

This is the part that makes the feature safe to offer at all.

A keyboard has no reset hole, and the flash sectors at the end of the chip
survive a UF2 write — so a password stored there would otherwise be permanent.
Instead, **the stored record is tagged with the build id of the firmware that
wrote it**, and a firmware that reads a record from a different build ignores it
and falls back to `env.h`.

So the recovery path is:

```sh
export PICO_SDK_PATH=/path/to/pico-sdk
cmake --build build            # any rebuild gets a fresh id
# hold BOOTSEL, copy build/nethid.uf2 to RPI-RP2
```

and the `PASSWORD` / `USER_LIST` values in `env.h` work again. On the console:

```
[auth-store] stored password was written by build 4f2a91c3, this is 8b0e7d15
             - ignoring it and using the compiled password
```

The id comes from `cmake/build_id.cmake`, regenerated by a custom target that
runs on **every** build, not at configure time. A configure-time value would sit
still across rebuilds and a reflash would then inherit the old password — the
one thing this must not do. The cost is that every build relinks; that is a few
seconds, and it buys the guarantee.

The rule is "written by the image that is running", not "newer wins". Flashing an
older firmware disowns the record too. Reflashing the *identical* image is not a
special case — a rebuild produces a new id even if nothing changed.

## What it is not

**It is not hashed.** Login is challenge-response: the device computes
HMAC-SHA256 keyed by the password, so it has to hold the password itself, not a
digest. The override sits in plaintext in flash — exactly as the compiled
password already sits in plaintext in the firmware image. Anyone who can dump
the flash could read the password before this feature existed, so it adds no
exposure; it does not add protection either. Flash is not a secret store.

**It is not available in WiFi setup mode.** `/api/password` is deliberately
absent from AP mode's allowlist. Setup mode exists to get a device onto a
network; letting it change the login would make "join the setup AP" a way to
take the device over. The panel hides itself there.

**It does not work over plain HTTP when `ALLOW_PLAINTEXT_AUTH=0`.** That setting
is a statement that no password may cross the network, and login honours it by
never sending one. A password *change* cannot — the new password has to reach
the device somehow. Rather than quietly making the setting a half-truth, the
endpoint refuses and the panel explains itself. Build with `-DENABLE_HTTPS=ON`
and both hold.

Over plain HTTP with plaintext auth allowed (the default), the panel warns that
the new password crosses the network in the clear. Logging in still does not.

## Rules

- The **current password is required**, even though the session is already
  authenticated. A password change is the one action that can lock the owner
  out, so it re-proves knowledge — which also means an unlocked browser someone
  walks up to cannot take the device away from you.
- Wrong guesses count towards the **same lockout** as the login page. Without
  that, this endpoint would be an unthrottled oracle for the password the login
  page carefully refuses to let you brute-force.
- Length is `WEB_PASSWORD_MIN_LEN` (8) to `AUTH_PW_MAX` (63). The lower bound is
  also what stops `""` arriving through a web form and disabling auth for the
  whole device; the deliberate way to run without a password is `PASSWORD ""` in
  `env.h`.
- On success, **every other session for that user is signed out** and the one
  that made the change is kept. Sessions opened with the old password must not
  survive it, but signing out the person who just changed it — on a device whose
  recovery path is a reflash — is the wrong reflex.
- Multi-user builds change **the signed-in user's** password only. Each user has
  their own override; clearing one does not touch another.
- There is no separate save step. The change applies immediately and the flash
  write is queued for core 0, because a password change you have to remember to
  save is one that silently reverts at the next power cycle.

## API

| | |
| --- | --- |
| `GET /api/password` | status only — never a password, not even a hash |
| `POST /api/password` | `{"current":"..","new":".."}` |
| `POST /api/password/reset` | `{"current":".."}` — back to the compiled password |

```json
{ "ok": true, "user": "admin", "multiuser": false,
  "min_len": 8, "max_len": 63,
  "changed": true,          // an override is in force
  "stored": true,           // flash holds a record this firmware accepted
  "build_id": "8b0e7d15",
  "secure": false,          // HTTPS
  "can_change": true, "why": "" }
```

Errors are specific on purpose — `wrong_password`, `locked` (with
`retry_after_s`), `bad_length`, `unchanged`, `plaintext_forbidden` — because
"rejected" for all of them sends you looking in the wrong place.

## Where it lives

| | |
| --- | --- |
| `src/auth_store.cpp` | the store, the build-id rule, the flash blob |
| `src/auth.cpp` | `user_password()` — the single place a password is read |
| `src/web.cpp` | the three endpoints |
| `cmake/build_id.cmake` | the per-build id |
| `tools/kbtest/auth_store_test.cpp` | host test, including the reflash transition |
| `tools/check/check_password_ui.js` | the panel, under jsdom |

Flash sector map, counted back from the end of flash:

| | |
| --- | --- |
| 1 | keymap |
| 2 | macros |
| 3 | wifi credentials |
| 4 | settings |
| 5 | autoclick slots |
| 6 | **passwords** |

`tools/kbtest/stubs/hardware/flash.h` fakes eight sectors so a host test covers
every one of them. It faked four for a long time, which put autoclick's sector
past the end of the array — its test was reading outside the buffer and only
happened not to crash. Raise it before adding a seventh store.

Every read of a password goes through `user_password()` in `src/auth.cpp`. Three
call sites used to reach into the user table directly; a fourth path that forgot
to would give a changed password that works for plaintext login but not for
challenge-response, or the reverse. A half-changed password is worse than one
that did not change.
